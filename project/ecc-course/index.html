# Soul —— 整个项目的「身份证」。这一行是 一级标题,宣告这份文件定义 ECC 是什么。

## Core Identity —— 核心身份。下面一句话自我介绍,是整个项目最重要的那句话。

ECC 是一个「生产级」AI 编程 插件:配了 30 个专家、135 个技能、60 个命令,还有自动化的 hook 工作流。

## Core Principles —— 五条「铁律」,教 AI 该怎么干活。

Agent-First:尽早把活儿交给对的专家(对应 hero 动画里的接力)。

Test-Driven:先写/更新测试,再相信改动。

Security-First:校验输入、保护密钥、保持安全默认。

Immutability:改状态时用「显式切换」而非偷偷改一个变量——避免难以追踪的副作用。

Plan Before Execute:复杂改动要先拆成清晰的阶段,而不是上来就写。

拆一位同事的「简历」：一个 agent 长什么样

每位专家同事的简历都是同一个结构：YAML 头（档案卡）+ 提示词（工作指南）。左边是规划师 planner 的简历原文。

agents/planner.md 
---
name: planner
description: Expert planning specialist for complex
  features and refactoring. Use PROACTIVELY when users
  request feature implementation, architectural changes,
  or complex refactoring.
tools: ["Read", "Grep", "Glob"]
model: opus
---
逐行翻译

name: planner —— 这位同事的工号/名字叫 planner（规划师）。系统派活时就喊这个名字。

description —— 自我介绍，也是「何时该派他」的触发条件：处理复杂功能和规划专家。PROACTIVELY（主动）是关键词——用户一提复杂需求，系统不用等点名，主动就派他。

tools —— 他被允许用的工具清单：Read（读文件）、Grep（搜内容）、Glob（找文件）。规划师只读不写——他只负责想，不动手改代码。

model: opus —— 用哪个大脑干活。opus 是更强的模型，规划这种费脑子的活配最强大脑，反过来简单活可以配小模型省钱。

🪪
四字段 = 一个 agent 的全部身份证

name（名字）、description（何时派他）、tools（能用啥工具）、model（用哪个大脑）。记住这四个字段，下次想新增一位专家同事，你就知道该往 YAML 头里填什么。

那条 command 怎么接你的口令？看它原文怎么写——$ARGUMENTS 就是「你喊命令时后面跟的那句话」。

commands/code-review.md 
---
description: Code review — local uncommitted changes
  or GitHub PR (pass PR number/URL for PR mode)
argument-hint: [pr-number | pr-url | blank for local review]
---

# Code Review

**Input**: $ARGUMENTS

If `$ARGUMENTS` contains a PR number, PR URL, or `--pr`:
→ Jump to **PR Review Mode** below.
逐行翻译

YAML 头里 argument-hint 提示你：这条命令后面可以跟一个 PR 编号、网址，或啥也不跟（默认审本地改动）。

$ARGUMENTS 是个前缀变量：代表「你喊命令时后面跟的那段话」。你喊 /code-review 123，它就变成 123。

下面是分支逻辑：如果你传的是 PR 编号或网址，就跳到「PR 审查模式」；否则默认审查本地没提交的改动。

同一条命令，靠 $ARGUMENTS 接不同输入，就能干两件相关但不同的活——这就是 command 的灵活之处。

03

Skills：把「正确做法」写成手册，AI 每次都照着干

同一段需求,这次 AI 写得好,下次它又忘了?问题不在 AI 记性差,在于没人给它留过一本 SOP 手册。

连锁咖啡店为什么每杯拿铁都一个味?

你让一个 裸 AI 写一个登录功能。第一次它写得很漂亮,第二次它又换了一套写法——因为没人告诉它「在我们这个项目里,登录就该这么写」。

连锁咖啡店不靠每个店员的发挥。它靠一本 SOP 手册:拿铁这一页写着几克豆、几度奶、打几秒。不管哪个店员翻开,出来的拿铁都一个样。

☕
没有手册的店员 = 裸 AI

凭感觉、凭记忆。今天高兴了多放一勺糖,明天走神了忘打奶泡。质量忽好忽坏——这就是你跟 AI 裸聊时的常态。

📖
有手册的店员 = 有 skill 的 AI

翻开「拿铁」这一页,按步骤做。换一个新店员(开一个新 AI 会话),出来的拿铁还是一个味。

📚
ECC 的 278 本手册

ECC 这个项目里塞了 278 个 skill。每本手册对应一类活:写新功能怎么写、改 bug 怎么改、提交代码前检查什么。

💡
一本手册 = 一本「可复用」的手册

skill 的灵魂就在「可复用」三个字。写一次,以后每次开新会话,AI 都自动翻开这本手册照着干。你不再是「每次都重新解释一遍该怎么写」,而是「一次写好规矩,终身受用」。

拆一本手册:一个 skill 到底长什么样

一个 skill 其实就两样东西:一个文件夹 + 一个 SKILL.md。手册的封皮是一段 YAML 头——它就是这本手册的「身份证」。我们来逐行翻译 ECC 里最厉害的那本手册 tdd-workflow。

手册封皮 
---
name: tdd-workflow
description: Use this skill when writing
  new features, fixing bugs, or
  refactoring code. Enforces test-driven
  development with 80%+ coverage
  including unit, integration, and E2E tests.
argument-hint: <path/to/*.plan.md>
metadata:
  origin: ECC
---
逐行翻译

name: tdd-workflow —— 这本手册叫什么名字。AI 用名字来找它:「我要用 tdd-workflow 这本」。

description: ... —— description:什么时候该翻开它。「写新功能、修 bug、重构代码时翻开我」。

Enforces test-driven development... —— 这本手册的核心规矩:强制 TDD,覆盖率 80% 起,覆盖 单元、集成、E2E 三种测试。

argument-hint: <path/to/*.plan.md> —— 提示用户:用这本手册时最好顺便给一份 .plan.md 计划文档 当输入。

origin: ECC —— 这本手册是从哪来的:它来自 ECC 这个项目(不是外部仓库)。

注意 description 这一句——它是整本手册里 AI 最在意的一句话。AI 会拿这句话和你的需求去对暗号:你说「帮我加个登录功能」,它一看 description 里写着「writing new features」,暗号对上了,就主动翻开这本手册。

skill 的三个关键问题

TDD 的灵魂:RED 🔴 → GREEN 🟢 → REFACTOR ♻️

ECC 里最值得琢磨的就是 tdd-workflow 这本手册。它给 AI 立了一条铁律——先写测试、看到测试失败、再写代码。这条铁律拆成三道关卡,就是 TDD 的全部精髓。

🔴
RED 关卡 —— 先写测试,运行,它必须失败

功能还没写,测试当然过不去——但这一步非跑不可。跑红了,才能证明「这个测试真的在测那个功能」,而不是一个永远都会过的假测试。这就是 RED 关卡。

🟢
GREEN 关卡 —— 写最少的代码,让测试变绿

现在才动笔写真正的功能代码。写完再跑同一个测试,它必须从红变绿(通过)。变绿了才算过关——这就是 GREEN 关卡:不是 AI 说「搞定了」,而是测试替你点头。

♻️
REFACTOR 关卡 —— 测试保持绿色的前提下,优化代码

功能跑通了,但代码可能写得丑。这一步你大胆整理——重命名、拆函数、删冗余。每改一点就跑一次测试,只要它还绿着,你就没改坏。这就是 REFACTOR:测试是安全带,放手整理不怕摔。

🛑
RED 不是「失败了再说」,而是「必须先失败」

新手最容易跳过 RED:先写好功能,再补个测试,一次性绿——图省事。但这样你永远不知道那个测试是不是真的在测东西。测试先红一次,是 TDD 给你的一张「测试质量保单」。

💡
最关键的洞察:RED/GREEN 是给 AI 上「证据」

裸 AI 干完活会说「我搞定了,放心吧」——它凭什么?凭感觉。有了 TDD skill,AI 不能再说空话,它必须拿出测试结果当证据:RED 证明测试有效,GREEN 证明功能写对。这就是 skill 把 AI 的「凭感觉」变成「有证据」的那一刻。

04

Hooks:给 AI 装上「自动刹车」的隐形质检员

skill 靠 AI 自觉翻开,可它偶尔偷懒跳过怎么办?hook 是那个「事件一发生,不管你想不想就强制执行」的自动闸。

上一节那本 TDD 手册写得再好,也架不住 AI 偶尔偷懒

上一节我们说,skill 是一本 AI 主动翻开的手册。你写了 TDD skill,写着「先写测试、再写代码」——AI 大概率会照做。可万一哪次它觉得「这次我赶时间,跳过吧」呢?

手册管不住「偷懒」。但如果你在提交代码的瞬间,装一道自动闸:「系统先帮你跑一遍测试,跑不过就物理拦住,谁都别想提交」——AI 想跳都跳不掉。这道闸,就是 hook。

🚗
skill = 司机自觉系安全带

司机大部分时候会记得系——但他可能忘、可能犯懒、可能赶时间跳过。手册是好东西,可它管不住「不愿意」。

🛑
hook = 车的自动刹车系统

你不用想着「该不该踩」,车自己判断。要追尾了——它替你刹死。不需要你同意,事件一到就强制触发。这是 hook 和 skill 最根本的不同。

⚙️
一句话定义 hook

在某个事件发生时,自动执行一段检查,该放行放行、该拦截拦截。AI 同意与否,无关紧要。

💡
全课最该记住的一句话:skill 靠自觉,hook 靠强制

这是 ECC 治理 AI 的两把钥匙。skill 把「正确做法」写成手册,靠 AI 主动遵循;hook 把「绝不能跳过的事」绑在事件上,靠系统强制触发。一个是软约束,一个是硬闸门。对付「AI 老犯同样的错」,你的终极武器永远是 hook。

注意 hook 在哪一步插入

它不在「推送之后」,也不在「AI 想之前」,而是卡在「AI 已经要推、但还没真推」的那个瞬间。这个「事件发生前的拦截点」就是 PreToolUse。记住这个时机,你就懂了 hook 为什么能「拦得住」。

hook 能绑在哪些时刻?六种事件

一个 hook 配置 = 一个 matcher(匹配什么情况)+ 一段 command(执行什么检查)。ECC 用的核心触发时刻一共六种,每个时刻都能挂自己的 hook。

🛑

PreToolUse

AI 准备用某个工具之前。拦还是放、提醒还是格式化,都靠它。这是最能「挡」的时刻。

✅

PostToolUse

AI 用完某个工具之后。常用来「自动善后」——比如刚改完代码,立刻自动跑一遍格式化。

⌨️

UserPromptSubmit

你按下回车、把话发给 AI 那一刻。能在话送进 AI 之前先过一道筛子(比如补上下文)。

🏁

Stop

AI 回答完毕、准备停下来时。可以在它「收工」前再做最后一道检查或总结。

📦

PreCompact

上下文窗口被压缩之前。能决定哪些历史该留、哪些可以丢。

🔔

Notification

系统需要你授权、或要弹个通知时。比如某个动作需要你点一下「允许」,就是它。

🧩
两个零件看懂所有 hook

不管挂在哪一种事件上,每个 hook 都拆成两块:matcher(什么情况下触发我)+ command(触发后跑什么检查)。这两块组合起来,就是 hook 的全部。下面我们就拆一个真实的最小 hook 看看。

拆一个最小 hook:跑长命令前提醒开 tmux

下面这段是 ECC 里真实的最小 hook。AI 一旦准备跑一个长命令(装依赖、跑测试),hook 就提醒它「最好开个 tmux,免得中途断了」。左边是 JSON 真身,右边拆成「事件 / matcher / command」三块讲清楚。

JSON 配置 
{
  "PreToolUse": [
    {
      "matcher": "tool == \"Bash\" &&
        tool_input.command matches
        \"(npm|pnpm|yarn|cargo|pytest)\"",
      "hooks": [
        {
          "type": "command",
          "command": "if [ -z \"$TMUX\" ]; then
            echo '[Hook] Consider tmux...' >&2; fi"
        }
      ]
    }
  ]
}
逐块翻译

"PreToolUse"(事件) —— 这条 hook 绑在「AI 准备用工具之前」这个时刻。六种事件选一个,它就只在那个时刻被触发。

"matcher"(什么时候) —— 匹配条件:「工具是 Bash,而且命令里包含 npm / pnpm / yarn / cargo / pytest」。也就是说,只有跑这些长命令才提醒,别的命令一概不烦你。

"command"(做什么) —— 触发后跑这段检查:「如果当前不在 tmux 里(说明没开持久会话),就往错误流打印一句提醒」。

整条 hook 的意思:AI 想跑长命令前,系统自动看一眼「你开 tmux 了吗」——没开就提醒你开,免得命令跑到一半断了白费功夫。AI 完全没法跳过,因为这是系统在它动手前自己跑的。

🔑
matcher 越精确,越不会误伤

注意 matcher 写的是「npm|pnpm|yarn|...」这种具体命令,而不是「所有 Bash 命令」。这是 ECC 的规矩——matcher 要精确,不要用大而无当的「一刀切」。写得越准,提醒就越只在真正该出现的时刻冒出来,不会烦你。

hook 到底靠什么「拦」?全靠一个退码

你可能会问:hook 跑完那一段检查,凭什么就能把 AI 拦住?答案藏在程序退出时吐出的那个数字里——exit code(退码)。

exit 0 放行。意思是「检查通过、没问题」。AI 该干嘛干嘛,就像 hook 没存在过一样。
exit 1 拦截。意思是「这次不行」。AI 的动作被物理挡住,没法继续——这就是 hook「强制」二字的来源。
RULES.md 节选 
## Hook Format
- Hooks use matcher-driven JSON
  registration and shell or Node entrypoints.
- Matchers should be specific instead
  of broad catch-alls.
- Exit 1 only when blocking behavior
  is intentional; otherwise exit 0.
逐条翻译

matcher-driven JSON registration —— hook 用 JSON 登记,靠 matcher 驱动;具体执行可以是一段 shell,也可以是一个 Node 入口。

Matchers should be specific —— matcher 要写得精确,别图省事写个「什么都匹配」的大筐。否则 hook 会到处乱触发,烦死人。

Exit 1 only when blocking is intentional —— 这句是灵魂:「只有当你故意要拦的时候,才退 1;其余情况一律退 0」。换句话说,hook 默认是「不挡」的,挡是深思熟虑后的选择。

这条规矩让 hook 既「拦得住该拦的」,又「不乱挡正常的操作」。退码 1 是把刀,要用得克制。

💡
退码哲学:1 是拦,0 是放

这是 hook 能「强制」的全部秘密。hook 跑完检查,返回一个数字给系统;系统看到 1 就把 AI 的动作掐断,看到 0 就放行。没有商量、没有「再试试」——一个数字定生死。所以你写 hook 时,想清楚「什么情况下退 1」就行,剩下的系统替你执行。

⚠️
常见坑:matcher 太宽或太窄

hook 配了却没触发,九成是 matcher 的问题。写得太宽(比如匹配所有命令),到处乱挡、烦到你想关掉它;写得太窄(比如把 npm 拼成了 NPM),该拦的时候一次都拦不住。调试 hook 的第一件事,永远是先怀疑 matcher。

逐段翻译

什么能原封不动地跨工具复用?——SKILL.md 是最 portable(可移植)的单位。

拆一个 module:它怎么决定「复制哪些文件夹、喂给哪些工具」

你点的每份套餐,本质是一组 module。每个 module 又是一小段 JSON,告诉安装器:「我要复制哪个文件夹、支持哪些阅读器、吃多少上下文」。下面是 rules-core 这个 module 的真身。

install-modules.json 
{
  "id": "rules-core",
  "kind": "rules",
  "description": "Shared and language rules for supported harness targets.",
  "paths": ["rules"],
  "targets": ["claude", "claude-project", "cursor",
              "codex", "zed", "gemini",
              "hermes", "kimi", "qwen", "openclaw"],
  "defaultInstall": true,
  "cost": "light"
}
逐字段翻译

id="rules-core":这个 module 的身份证号。套餐列表里写的「rules-core」就是指它。

kind="rules":它属于「规则」这一类——和 skills、hooks、commands 是不同类别。

paths=["rules"]:安装时,把仓库里 rules 这一个文件夹复制过去。一个 module 对应一两个文件夹。

targets=[...十个工具...]:它支持喂给这十个阅读器。这就是可移植性的来源——同一份规则,十个工具都能读。

defaultInstall=true:默认装。哪怕最小套餐也带上它,因为是地基。

cost="light":吃上下文很「轻」。cost 分 light/medium/heavy,点套餐时靠它权衡。

三个字段串起整个安装逻辑

记住 profile → module → paths/targets 这条链:你选套餐,套餐点模块,模块决定复制哪个文件夹、喂给哪些工具。ECC 的安装就这么简单——没有黑魔法,全是查表 + 复制。

四份套餐怎么选 + 一道「别贪多」警示

ECC 预设了四份 profile。挑一份最像你的就行——别一上来就 full,那是给「啥都想试试」的人准备的陷阱。

🥗

minimal(最小)

适合谁:只想给 AI 加点规矩、不想装运行时的人。装什么:rules + agents + commands + 平台配置,没有 hook 运行时。轻重:最轻,几乎不吃上下文。

🍱

core(核心)

适合谁:想要完整 harness baseline 的人。装什么:minimal 的全部 + hook 运行时 + 工作流质量。轻重:轻,自动闸开始生效。

🍳

developer(开发者·推荐)

适合谁:大多数 ECC 用户、日常写代码的人。装什么:core 的全部 + 框架语言 + 数据库 + 编排。轻重:中等,够用又不撑。

🍗

full(全装·慎选)

适合谁:真正需要全部 23 个模块的人(很少)。装什么:所有已分类模块。轻重:重——上下文窗口会被显著挤占,AI 可能变迟钝。

⚠️
别贪多:full 不是「最好」,是「最危险」

新手最容易犯的错就是「既然有 full,那我肯定选 full」。错。装太多 = 挤爆上下文 = AI 变笨。从 developer 起步,觉得不够再加——这比「全装了再说」聪明得多。compact 不是好事,是危险信号。

小试一下:你会怎么选?

四道情景题,看看「点套餐」和「可移植」这两件事你吃透没有。

Q1:你是个全栈开发者,前后端都写、要碰数据库。该点哪份 profile?

Q2:朋友推荐你「直接上 full,功能最全」。为什么这不是好主意?

Q3:你想让同一个 skill 在 Cursor 和 Codex 里都能用。核心靠什么?

Q4:你点了 developer 套餐。安装器接下来怎么决定「复制哪些文件夹」?

五节课走完:ECC 到底给了你什么

还记得第一节的比喻吗——ECC 是给 AI 装的一个「操作系统」。现在你已经把这个系统从里到外看了一遍。把五节课浓缩成五句话,这就是你以后指挥 AI 时的底座。

🖥️
① ECC = 给 AI 装操作系统

它把散落的规矩、手册、自动闸、外线接口,组织成一个统一平台。你不用一次次重复教 AI,装一次,它就「带着这套规矩」干活。

👥
② 六大角色各司其职

agent 是同事、skill 是手册、command 是口令、hook 是质检闸、rule 是铁律、MCP 是外线电话。记住这六个岗位,你就有了调试 AI 的组织架构图。

📜
③ skill = AI 主动遵循的手册

一份 SKILL.md 告诉 AI「什么时候、怎么干某件事」。它靠 AI 自己判断该不该用——灵活,但需要 AI 自觉。最可移植的单位,七个工具通吃。

🚦
④ hook = 强制的自动闸

在关键节点硬性触发的脚本,不靠 AI 自觉。「提交前必跑测试」「安全代码必复审」——它兜的是 skill 兜不住的底线。

🍱
⑤ 按需点套餐,别撑爆上下文

装 ECC 像点套餐:minimal/core/developer/full 任选一份。上下文窗口是稀缺资源,装太多 AI 反而变笨。从 developer 起步,够用就好。

🎯
你现在已经拥有的能力

学完这五节,你已经能:看懂任何「给 AI 写说明书」类项目的本质;分清 skill 和 hook 的差别;读懂 profile/module/targets 这些安装字段;知道为什么一套 SKILL.md 能喂饱七个工具;更懂得怎么 调教 AI——别让它一次记太多,给它留足思考的脑子。

🚀
最后一句话

ECC 不是某个神奇工具,而是一种思路:把「怎么用 AI 干活」这件事本身,变成一套可维护、可移植、可组合的操作系统。理解了这个思路,你看到的就不只是一个仓库——而是一种组织 AI 能力的通用方法。现在,你也能为自己的 AI 搭一套操作系统了。
