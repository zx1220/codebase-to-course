01

这是什么：一个把「不能订阅的网站」翻译成 RSS 的同声传译

你天天刷的 B站、微博、推特为什么偏偏订阅不了？答案需要一个「中间人」。

先抛个问题：为什么博客能订阅，B站 却不能？

你可能已经用 RSS 阅读器订阅过博客。但你有没有想过——为什么 RSS 这种好东西，B站、微博、推特偏偏不提供？

因为它们各自只说自己的「方言」，而你的阅读器只听得懂一种「世界语」。中间需要一个翻译——这个翻译就是 RSSHub。

📺
你喜欢的网站（B站 / 微博 / 推特 / GitHub）

各说各的「方言」：有的吐 JSON，有的只有网页。没有一个统一的订阅格式。

📖
你的 RSS 阅读器

只听得懂一种「世界语」：RSS 格式。它不会去 B站 爬数据，也不会读网页——给它 RSS，它才认。

🌐
RSSHub —— 中间的同声传译

你递一个 B站地址给它，它替你去 B站 抓数据，翻译成 RSS，再交还给你的阅读器。这就是它的全部存在意义。

💡
记住这个比喻：RSSHub = 网站翻译官

整个项目的灵魂就一句话——把「不提供 RSS 的网站」变成「能订阅的 RSS 源」。后面所有架构细节，都是为了让这个翻译又快又稳又多语种。

一个 URL = 一个订阅源

换一个命名空间、换一个参数，就是完全不同的订阅源。RSSHub 用「地址本身」来描述你想要什么——这是它最巧妙的设计，也是理解后面「路由」的钥匙。

RSSHub 凭什么这么好用

它不只翻译一个网站。下面四件事合在一起，才让它成了「万物皆可 RSS」的那个工具。

🌐

1600+ 个网站源

B站、微博、推特、GitHub、知乎、豆瓣……几乎你想得到的主流网站，都已经有人写好了翻译规则，开箱即用。

🔗

一个 URL 就能订阅

不用装插件、不用配账号。把一条 RSSHub 地址丢进阅读器，就开始收更新。地址本身就是「我想要什么」。

⚡

自带 缓存省流量

同一个源短时间内被多次请求时，RSSHub 不会傻乎乎每次都去爬一遍目标网站，而是先返回缓存好的结果，又快又省事。

🛠️

可以自己部署

除了用官方公开服务器，你也能在自己电脑或服务器上跑一份 RSSHub，完全掌控数据和速度。代码是开源的。

02

一条订阅源的诞生 · 路由文件解剖

看懂一个文件，就看懂了 RSSHub 八成的代码。

RSSHub 的「灵魂」长什么样？

上一模块我们看到 /bilibili/user/dynamic/2267573 能订阅一个 B站 UP 主。但 RSSHub 是怎么知道「遇到 bilibili 就调 B站、遇到 weibo 就调微博」的？

答案藏在一种叫路由文件的东西里——它就是 RSSHub 的灵魂。

🍽️
核心比喻：外卖菜单 + 后厨配方

把整个 lib/routes/ 想象成一条美食街。每个文件夹就是「一家餐厅」（比如 B站、微博、GitHub），文件夹里每个 .ts 文件就是菜单上的一道菜。菜单上写这道菜叫什么、长什么样；后厨配方（handler 函数）写怎么买菜、怎么炒、怎么装盘。

这条街上有 1600 多家「餐厅」

RSSHub 用一个极简约定组织了 1600+ 个网站源：一个文件夹 = 一个网站，一个 .ts 文件 = 一条订阅源。

lib/routes/ 这条「美食街」——所有网站源都在这里
bilibili/ 「B站这家餐厅」(namespace)
namespace.ts 这家店的「身份证」
article.ts 一道菜：UP主图文
dynamic.ts 一道菜：UP主动态
video.ts 一道菜：视频
… 50 多个文件 = 50 多道菜
weibo/ 「微博这家餐厅」
github/ 「GitHub这家餐厅」
… 1600+ 个文件夹

每个餐厅还有一个 namespace.ts——它的身份证。

先看「身份证」：namespace.ts

每个网站文件夹里都有一个 namespace.ts，短短几行，只声明这家餐厅是谁。

CODE 
import type { Namespace } from '@/types';

export const namespace: Namespace = {
    name: '哔哩哔哩 bilibili',
    url: 'www.bilibili.com',
    lang: 'zh-CN',
};
大白话翻译

引入一个「类型模板」，告诉编辑器「我要写的是一份身份证」。

name 是显示名——用户在文档里看到的中文+英文名。

url 是目标网站地址——这家餐厅对应的「菜市场」。

lang 是语言——B站是中文站，所以标 zh-CN。

就这样。身份证只管「我是谁」，不管怎么做菜。

再看「菜单」：route 对象声明

每个 .ts 文件都 export 一个 route 对象，声明这条源「负责什么 URL、叫什么名字、谁在维护」。

后厨配方：handler 函数在干什么

这是同一个 article.ts 里的 handler。它干三件事：① 拿到 API JSON 数据、② 解析每一篇文章、③ 打包返回。

CODE 
async function handler(ctx) {
    const uid = ctx.req.param('uid');
    const name = await cache.getUsernameFromUID(uid);
    const response = await got({
        method: 'get',
        url: `https://api.bilibili.com/x/polymer/web-dynamic/v1/opus/feed/space?host_mid=${uid}`,
        headers: {
            Referer: `https://space.bilibili.com/${uid}/article`,
        },
    });
    const data = response.data.data;
    const title = `${name} 的 bilibili 图文`;
        // ……中间省略：用 load() 解析每篇文章网页、提取正文和日期……
    return {
        title,
        link,
        description,
        item,
    };
}
大白话翻译

这是一个异步函数，ctx 是这次请求的「上下文」。

先从 URL 里取出 uid，再查缓存拿用户名。

got(...) 是HTTP 客户端，RSSHub 派它去敲 B站 的接口拿数据。

中间省略的部分：用 load()（cheerio）配合 CSS 选择器）解析每篇文章，用 cookie 通过反爬。

Promise.all 是「同时跑多个任务、等它们全部完成」的写法——比如同时解析 20 篇文章。

注意最后这几行：它返回的是一个纯数据对象，不是 RSS，不是 XML。

最关键的设计：handler 只返回「数据」

handler 不碰 RSS XML，不写标签，不管输出长什么样——它只吐出一个数据对象。这是整个 RSSHub 最聪明的地方。

CODE 
return {
    title,
    link,
    description,
    item,
};
大白话翻译

title 是这整个订阅源的名字（「某某 的 bilibili 图文」）。

link 是回链——点进去能去到 B站主页。

description 是一句话简介。

item 是一个数组，装着每一条内容（每篇文章一个对象）。

就这些。handler 完全不知道 RSS 长什么样——RSS 的拼接由别人管。这就是 5000+ 路由文件能共用一套渲染引擎的根本原因。

💡
大智慧：分离关注点 (Separation of Concerns)

handler 只管「去哪拿数据、拿什么」，RSS 长什么样由另一个渲染引擎负责。抓取逻辑和输出格式彻底解耦——同一套抓取代码能同时输出 RSS / Atom / JSON。这是软件工程里最重要的思想之一：让每个部分只干一件事。

注意到那条「分支A · 命中」了吗？如果之前抓过，handler 根本不会跑。这就是为什么同一个订阅源「第一次慢、第二次快」。

机场安检 + 流水线

把请求想象成一个旅客进机场：先过安检门查钥匙、再过登机牌扫描查缓存、走到对应登机口（路由匹配），handler 干完活回来，还要经过打包区美化、最后贴标签出港。每一道关都是一个中间件，按固定顺序排队。

1
accessControl 查访问密钥

你设了 ACCESS_KEY 吗？没钥匙的请求直接被拦下，返回 HTTP 状态码 403。

2
cache 查有没有现成的

cache 查 Redis：这个地址之前抓过吗？抓过就秒回。

3
路由匹配找到 handler

缓存没命中？放行。Web 框架根据 URL 找到对应的 handler 函数。

4
handler 抓数据

handler 调外部 API、解析 HTML、返回一个数据对象（上一模块见过的那个）。

5
parameter / template 美化并渲染

数据对象往回飞，parameter 支持 ?filter ?limit 等参数，template 把它渲染成 RSS。

完整的流水线总图

真实的注册顺序更长——下面是 lib/app-bootstrap.tsx 里一长串 app.use(...) 的「翻译版」。请求从上往下穿过每一道关，响应再从下往上穿回来。

注册顺序 
trimTrailingSlash  → 去掉 URL 末尾多余的斜杠
compress           → 压缩响应，省流量
logger             → 打印日志
trace              → 链路追踪（调试用）
honeybadger/sentry → 错误上报（出 bug 自动报警）
accessControl      → 【关卡1】查访问密钥，没钥匙就 403
debug              → 统计调试信息
template           → 【关卡】在 handler 之后渲染输出
header             → 设置响应头、ETag
antiHotlink        → 防图片盗链
parameter          → 【关卡】美化数据、支持 ?filter ?limit 等
cache              → 【关卡2】查缓存，没缓存才放行去 handler

然后才路由匹配 → 跑 handler
大白话

前面这几道是「基础设施」——去斜杠、压缩、记日志、出错报警，跟业务无关。

accessControl 是第一道业务关卡：查密钥。

template / header / parameter 这几道在 handler 「之后」才干活，给数据做加工。

cache 是最后一道关卡——它命中就直接返回，handler 根本不跑。

所有关卡都过了，才轮到路由匹配 → 真正跑 handler。

四个典型的中间件「角色」

每个中间件就像流水线上一个工位的工人，各管一摊事。记住这四个角色，80% 的 bug 你都能定位到是哪个工位出了问题。

🛂

accessControl · 守门员

站在最前门查钥匙。你设了 ACCESS_KEY，它就核对你的请求带没带对的密钥，没带就 403 直接挡回去。

💾

cache · 省钱大师

查 Redis 里有没有现成结果。命中就秒回、连 handler 都不跑；没命中才放行去抓新数据。

✨

parameter · 美颜滤镜

handler 干完活之后才上场。它支持 ?limit=10、?filter=xxx 等参数，对返回的数据做裁剪和美化。

🏷️

template · 翻译成 RSS

把那个数据对象翻译成阅读器认得的 RSS/Atom/JSON 格式。抓取和输出分开——这是下一模块的主角。

一个通用的大智慧 · 洋葱模型

把每个中间件想象成洋葱的一层皮。请求从外面一层层穿进去（accessControl → cache → ... → handler），handler 处理完，响应再一层层穿出来（... → parameter → template）。这就是洋葱模型。

💡
这是 Web 框架的通用思想

请求一层层穿进去、响应一层层穿出来——Express、Koa、Hono 这些Web 框架全都这么干。RSSHub 用的是 Hono。学会这套思路，你看任何一个现代 Web 服务都能秒懂它怎么运转。

这意味着每一层中间件都有「两次机会」：请求穿过它时干一次活（比如 accessControl 查钥匙），响应穿回来时还能再干一次活（比如 template 渲染、header 设置 ETag）。出问题的时候，先想清楚是「进去时」还是「出来时」出的问题，你就锁定了一半的代码范围。

中文翻译

开一个多路开关，根据 outputType 决定走哪条路——它就是用户在 URL 里写的 ?format=。

如果写的是 rss3，把数据交给 rss3() 函数转成 JSON 返回（一种特殊格式）。

如果写的是 json：先设一个 Content-Type 告诉对方「这是 JSON」，再把数据交给 json() 渲染。

如果写的是 atom，把数据塞进一个叫 <Atom> 的组件去渲染。

注意一个细节：所有分支用的都是同一个 result。数据没变，变的只是「把它喂给哪个渲染器」。这就是「同数据多视图」。

聪明的缓存与防护 · 不被自己打垮

一个热门源被一万个人同时订阅，RSSHub 却只去源头抓一次——它怎么做到的？

把 RSSHub 想象成一个编辑部

RSSHub 是个公开服务。一个大 V 的微博，可能被成千上万个阅读器订阅——如果每个阅读器来一次，RSSHub 就去微博抓一次，微博分分钟把它封号。

它的解法是把整个系统想成一个只有一个跑腿记者的编辑部。前台（一个 中间件）做了两件聪明事：

🗂️
复印存档 · 缓存（cache）

记者抢回来的新闻复印一份存档。后来要同一条新闻的人，直接拿复印件，记者不用再跑一趟。

🏃
候客休息区 · 单飞（single-flight）

如果记者正在抢这条新闻，其他人先进休息区坐着。记者一回来，大家一起看结果，绝不重复派第二趟。

⚠️
惊群效应（thundering herd）

这是高并发系统的经典陷阱：缓存一旦失效，所有等待的请求同时涌向目标网站。RSSHub 用单飞机制化解——只放行一个，其余原地等。记住这个词，跟 AI 聊性能时它一听就懂。

看完记住一句话：handler 只跑了一次。这就是单飞的全部魔法——它把一万次重复劳动压成了一次。

单飞的五个时间步

把上面动画拆成五张卡。这是claim（占位）+ 等待循环的完整时序，也是高并发系统的看家本领：

1
缓存查不到

请求先 get(key) 查一次存货。没命中，才进入下一步——绝大多数请求其实都死在这一步之前，直接吃缓存返回了。

2
抢占位（claim）

没命中的请求都去抢一个「占位标记」。这是一个原子操作——只有第一个抢到的会拿到「true」，其余全拿到「false」。

3
抢到的去抓数据

拿到 true 的那个请求，放行去 handler，跑完整个流水线、抓回最新内容。

4
其他人原地轮询等待

拿到 false 的请求进 while 循环，每隔几秒 轮询（polling）一次：占位还在吗？还在就继续等。

5
抓完共享结果

抢到的人把结果存进缓存、清掉占位。等待中的人下一次轮询发现占位没了，直接 get(key) 拿缓存结果返回。大家用的是同一份数据。

💡
原子操作：要么全做、要么不做，中间没人能插队

第 2 步的 claim 之所以必须「原子」，是因为「检查占位 + 设置占位」如果中间能被打断，两个请求可能都查到「没人占」、然后都把自己设成抓取者——单飞当场失效。这是并发编程的基石概念，记住它，你看任何锁机制都能举一反三。

代码里的 claim：一段 Lua 脚本搞定原子占位

占位逻辑由 Redis 实现。核心是中间那行 eval：把「检查 + 设置」写成一段脚本交给 Redis 一口气执行，中间没人能插队。

CODE · lib/utils/cache/index.ts 
            globalCache.claim = async (key, maxAge) => {
                if (!key || !cacheModule.status.available || !redisClient) {
                    return true;
                }
                const result = await redisClient.eval("if redis.call('GET', KEYS[1]) == '1' then return 0 end redis.call('SET', KEYS[1], '1', 'EX', ARGV[1]) return 1", 1, key, maxAge);
                return result === 1;
            };
说人话

claim 就是「认领、占位」——尝试把这个 key 标记成「有人正在抓」。

没传 key、或 Redis 没连上，就直接返回 true（退化成普通模式，大家都能抓）。

真正核心是 eval 那行：一段 Lua 脚本交给 Redis「一口气」跑完。

脚本逻辑——先查 key 是不是已经是 1：是就返回 0（别人占了，你抢不到）；否则设成 1 带过期时间，返回 1（你抢到了）。

因为 Redis 单线程顺序执行，这段「检查 + 设置」中间不可能有人插队——这就是原子操作。

中间件里：抢到了去抓，没抢到的进休息区

占位的判定和等待循环，都活在 cache 中间件里。左边两段代码，右边一行行翻译成「编辑部大白话」：

CODE · lib/middleware/cache.ts 
    let value = await cacheModule.globalCache.get(key);

    // Doesn't hit the cache? Try to become the fetcher and let others know!
    let isRequesting = false;
    if (!value) {
        isRequesting = !(await cacheModule.globalCache.claim(controlKey, config.cache.requestTimeout));
    }

    if (isRequesting) {
        let retryTimes = process.env.NODE_ENV === 'test' ? 1 : 10;
        let bypass = false;
        while (retryTimes > 0) {
            // eslint-disable-next-line no-await-in-loop
            await new Promise((resolve) => setTimeout(resolve, process.env.NODE_ENV === 'test' ? 3000 : 6000));
            // eslint-disable-next-line no-await-in-loop
            if ((await cacheModule.globalCache.get(controlKey)) !== '1') {
                bypass = true;
                break;
            }
            retryTimes--;
        }
        if (!bypass) {
            throw new RequestInProgressError('This path is currently fetching, please come back later!');
        }
        value = await cacheModule.globalCache.get(key);
    }
说人话

先 get(key) 查一次存货——这是「先看复印件有没有」。

没命中（!value）才去 claim 抢占位。! 取反：claim 返回 false（没人占）时，isRequesting 才是 true——意思是「该我抓了」。

注意：isRequesting 为 true 的是抢到的抓取者，会跳过下面整个 if，直接往下走去 handler。

进了 if 的是没抢到的人：开一个 while 轮询循环，默认重试 10 次。

每轮先睡 6 秒（test 环境 3 秒），再去查占位 key 还在不在——这就是在休息区坐着等的动作。

占位被清掉了（说明抓取者完工），就 break 跳出，去拿缓存结果。

要是重试 10 次还没好，就抛 RequestInProgressError——对外就是 503「正在抓取请稍后」。

抓到之后：存进缓存，盖上 5 分钟保质期

抢到的人抓完数据，最后一步是「归档」。除非响应明确要求不缓存，否则把结果整份存进缓存，并设一个 TTL：

CODE · lib/middleware/cache.ts 
    const data: Data = ctx.get('data');
    if (ctx.res.headers.get('Cache-Control') !== 'no-cache' && data) {
        data.lastBuildDate = new Date().toUTCString();
        ctx.set('data', data);
        const body = JSON.stringify(data);
        await cacheModule.globalCache.set(key, body, config.cache.routeExpire);
    }
说人话

拿到流水线抓回来的 data。

除非响应头明确写了 no-cache，否则进入归档流程。

给数据盖一个时间戳 lastBuildDate，序列化成字符串。

set(key, body, routeExpire)——存进缓存，过期时间默认 300 秒 = 5 分钟。

这 5 分钟内再来任何人，第一屏的 get(key) 直接命中，根本走不到 claim——这就是「一万次请求只抓一次」的来源。

RSSHub 为什么不崩溃？三句哲学

1600+ 个源、社区维护，却没乱成一锅粥。秘密就藏在这三个设计选择里——它们也是你能搬走的核心收获。

📁

约定优于配置

文件夹 = 网站，文件 = 源。1600+ 源靠这套文件系统约定组织，不用维护中央路由表。

你能怎么用：自己的项目也定死一条「放哪=是什么」的规矩，省掉一堆 if/else。

🔀

关注点分离

handler 只抓数据，缓存 / 美化 / 渲染全交给中间件。

你能怎么用：写函数时问自己「这段是不是在干两件事」——是，就拆成两个。

🛡️

用聪明工程保护自己

单飞缓存防惊群，原子操作防竞态。

你能怎么用：凡是「很多人同时抢同一份资源」的地方，都想想「谁能帮我把并发收敛成一个」。
