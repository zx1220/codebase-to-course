聪明的缓存与防护 · 不被自己打垮

一个热门源被一万个人同时订阅，RSSHub 却只去源头抓一次——它怎么做到的？

把 RSSHub 想象成一个编辑部

RSSHub 是个公开服务。一个大 V 的微博，可能被成千上万个阅读器订阅——如果每个阅读器来一次，RSSHub 就去微博抓一次，微博分分钟把它封号。

它的解法是把整个系统想成一个只有一个跑腿记者的编辑部。前台（一个 中间件）做了两件聪明事：

🗂️
复印存档 · 缓存（cache）

记者抢回来的新闻复印一份存档。后来要同一条新闻的人，直接拿复印件，记者不用再跑一趟。

🏃
候客休息区 · 单飞（single-flight）

如果记者正在抢这条新闻，其他人先进休息区坐着。记者一回来，大家一起看结果，绝不重复派第二趟。

⚠️
惊群效应（thundering herd）

这是高并发系统的经典陷阱：缓存一旦失效，所有等待的请求同时涌向目标网站。RSSHub 用单飞机制化解——只放行一个，其余原地等。记住这个词，跟 AI 聊性能时它一听就懂。

看完记住一句话：handler 只跑了一次。这就是单飞的全部魔法——它把一万次重复劳动压成了一次。

单飞的五个时间步

把上面动画拆成五张卡。这是claim（占位）+ 等待循环的完整时序，也是高并发系统的看家本领：

1
缓存查不到

请求先 get(key) 查一次存货。没命中，才进入下一步——绝大多数请求其实都死在这一步之前，直接吃缓存返回了。

2
抢占位（claim）

没命中的请求都去抢一个「占位标记」。这是一个原子操作——只有第一个抢到的会拿到「true」，其余全拿到「false」。

3
抢到的去抓数据

拿到 true 的那个请求，放行去 handler，跑完整个流水线、抓回最新内容。

4
其他人原地轮询等待

拿到 false 的请求进 while 循环，每隔几秒 轮询（polling）一次：占位还在吗？还在就继续等。

5
抓完共享结果

抢到的人把结果存进缓存、清掉占位。等待中的人下一次轮询发现占位没了，直接 get(key) 拿缓存结果返回。大家用的是同一份数据。

💡
原子操作：要么全做、要么不做，中间没人能插队

第 2 步的 claim 之所以必须「原子」，是因为「检查占位 + 设置占位」如果中间能被打断，两个请求可能都查到「没人占」、然后都把自己设成抓取者——单飞当场失效。这是并发编程的基石概念，记住它，你看任何锁机制都能举一反三。

代码里的 claim：一段 Lua 脚本搞定原子占位

占位逻辑由 Redis 实现。核心是中间那行 eval：把「检查 + 设置」写成一段脚本交给 Redis 一口气执行，中间没人能插队。

CODE · lib/utils/cache/index.ts 
            globalCache.claim = async (key, maxAge) => {
                if (!key || !cacheModule.status.available || !redisClient) {
                    return true;
                }
                const result = await redisClient.eval("if redis.call('GET', KEYS[1]) == '1' then return 0 end redis.call('SET', KEYS[1], '1', 'EX', ARGV[1]) return 1", 1, key, maxAge);
                return result === 1;
            };
说人话

claim 就是「认领、占位」——尝试把这个 key 标记成「有人正在抓」。

没传 key、或 Redis 没连上，就直接返回 true（退化成普通模式，大家都能抓）。

真正核心是 eval 那行：一段 Lua 脚本交给 Redis「一口气」跑完。

脚本逻辑——先查 key 是不是已经是 1：是就返回 0（别人占了，你抢不到）；否则设成 1 带过期时间，返回 1（你抢到了）。

因为 Redis 单线程顺序执行，这段「检查 + 设置」中间不可能有人插队——这就是原子操作。

中间件里：抢到了去抓，没抢到的进休息区

占位的判定和等待循环，都活在 cache 中间件里。左边两段代码，右边一行行翻译成「编辑部大白话」：

CODE · lib/middleware/cache.ts 
    let value = await cacheModule.globalCache.get(key);

    // Doesn't hit the cache? Try to become the fetcher and let others know!
    let isRequesting = false;
    if (!value) {
        isRequesting = !(await cacheModule.globalCache.claim(controlKey, config.cache.requestTimeout));
    }

    if (isRequesting) {
        let retryTimes = process.env.NODE_ENV === 'test' ? 1 : 10;
        let bypass = false;
        while (retryTimes > 0) {
            // eslint-disable-next-line no-await-in-loop
            await new Promise((resolve) => setTimeout(resolve, process.env.NODE_ENV === 'test' ? 3000 : 6000));
            // eslint-disable-next-line no-await-in-loop
            if ((await cacheModule.globalCache.get(controlKey)) !== '1') {
                bypass = true;
                break;
            }
            retryTimes--;
        }
        if (!bypass) {
            throw new RequestInProgressError('This path is currently fetching, please come back later!');
        }
        value = await cacheModule.globalCache.get(key);
    }
说人话

先 get(key) 查一次存货——这是「先看复印件有没有」。

没命中（!value）才去 claim 抢占位。! 取反：claim 返回 false（没人占）时，isRequesting 才是 true——意思是「该我抓了」。

注意：isRequesting 为 true 的是抢到的抓取者，会跳过下面整个 if，直接往下走去 handler。

进了 if 的是没抢到的人：开一个 while 轮询循环，默认重试 10 次。

每轮先睡 6 秒（test 环境 3 秒），再去查占位 key 还在不在——这就是在休息区坐着等的动作。

占位被清掉了（说明抓取者完工），就 break 跳出，去拿缓存结果。

要是重试 10 次还没好，就抛 RequestInProgressError——对外就是 503「正在抓取请稍后」。

抓到之后：存进缓存，盖上 5 分钟保质期

抢到的人抓完数据，最后一步是「归档」。除非响应明确要求不缓存，否则把结果整份存进缓存，并设一个 TTL：

CODE · lib/middleware/cache.ts 
    const data: Data = ctx.get('data');
    if (ctx.res.headers.get('Cache-Control') !== 'no-cache' && data) {
        data.lastBuildDate = new Date().toUTCString();
        ctx.set('data', data);
        const body = JSON.stringify(data);
        await cacheModule.globalCache.set(key, body, config.cache.routeExpire);
    }
说人话

拿到流水线抓回来的 data。

除非响应头明确写了 no-cache，否则进入归档流程。

给数据盖一个时间戳 lastBuildDate，序列化成字符串。

set(key, body, routeExpire)——存进缓存，过期时间默认 300 秒 = 5 分钟。

这 5 分钟内再来任何人，第一屏的 get(key) 直接命中，根本走不到 claim——这就是「一万次请求只抓一次」的来源。
