机场安检 + 流水线

把请求想象成一个旅客进机场：先过安检门查钥匙、再过登机牌扫描查缓存、走到对应登机口（路由匹配），handler 干完活回来，还要经过打包区美化、最后贴标签出港。每一道关都是一个中间件，按固定顺序排队。

1
accessControl 查访问密钥

你设了 ACCESS_KEY 吗？没钥匙的请求直接被拦下，返回 HTTP 状态码 403。

2
cache 查有没有现成的

cache 查 Redis：这个地址之前抓过吗？抓过就秒回。

3
路由匹配找到 handler

缓存没命中？放行。Web 框架根据 URL 找到对应的 handler 函数。

4
handler 抓数据

handler 调外部 API、解析 HTML、返回一个数据对象（上一模块见过的那个）。

5
parameter / template 美化并渲染

数据对象往回飞，parameter 支持 ?filter ?limit 等参数，template 把它渲染成 RSS。

完整的流水线总图

真实的注册顺序更长——下面是 lib/app-bootstrap.tsx 里一长串 app.use(...) 的「翻译版」。请求从上往下穿过每一道关，响应再从下往上穿回来。

注册顺序

compress           → 压缩响应，省流量
logger             → 打印日志

template           → 【关卡】在 handler 之后渲染输出
header             → 设置响应头、ETag
antiHotlink        → 防图片盗链
parameter          → 【关卡】美化数据、支持 ?filter ?limit 等
cache              → 【关卡2】查缓存，没缓存才放行去 handler

然后才路由匹配 → 跑 handler
大白话

前面这几道是「基础设施」——去斜杠、压缩、记日志、出错报警，跟业务无关。

accessControl 是第一道业务关卡：查密钥。

template / header / parameter 这几道在 handler 「之后」才干活，给数据做加工。

cache 是最后一道关卡——它命中就直接返回，handler 根本不跑。

所有关卡都过了，才轮到路由匹配 → 真正跑 handler。

四个典型的中间件「角色」

每个中间件就像流水线上一个工位的工人，各管一摊事。记住这四个角色，80% 的 bug 你都能定位到是哪个工位出了问题。

🛂

accessControl · 守门员

站在最前门查钥匙。你设了 ACCESS_KEY，它就核对你的请求带没带对的密钥，没带就 403 直接挡回去。

💾

cache · 省钱大师

查 Redis 里有没有现成结果。命中就秒回、连 handler 都不跑；没命中才放行去抓新数据。

✨

parameter · 美颜滤镜

handler 干完活之后才上场。它支持 ?limit=10、?filter=xxx 等参数，对返回的数据做裁剪和美化。

🏷️

template · 翻译成 RSS

把那个数据对象翻译成阅读器认得的 RSS/Atom/JSON 格式。抓取和输出分开——这是下一模块的主角。

放大看 cache 关卡怎么工作

缓存关卡是整条流水线上最精巧的一站。左边是 lib/middleware/cache.ts 的真实代码，右边逐行翻译——注意工程师那些藏在代码里的小心思。

    const format = `:${ctx.req.query('format') || 'rss'}`;
    const limit = ctx.req.query('limit') ? `:${ctx.req.query('limit')}` : '';
    const key = 'rsshub:koa-redis-cache:' + h64ToString(requestPath + format + limit);
    const controlKey = 'rsshub:path-requested:' + h64ToString(requestPath + format + limit);

    if (value) {

大白话

拿到请求的地址，比如 /bilibili/user/123。

再加上格式（默认 rss）和数量限制，拼成一个完整的「请求签名」。

用 xxhash 把这个长签名压成一个短字符串——长地址当缓存 key 太占地方，工程师特意压短省 Redis 内存。

这就成了 Redis 里查缓存的钥匙。

接下来去 Redis 查：这把钥匙有对应的值吗？

命中了！直接返回 HTTP 200，并在响应头偷偷贴个「HIT」小标签（你可以用浏览器开发者工具看到）。

把缓存里的数据塞回去，然后调 next() 继续走流水线——但后面的 handler 不会重新抓，因为数据已经在了。

注意这个 return：命中就直接结束，handler 那一站根本不会跑。这就是「省事关卡」的精髓。

一个通用的大智慧 · 洋葱模型

把每个中间件想象成洋葱的一层皮。请求从外面一层层穿进去（accessControl → cache → ... → handler），handler 处理完，响应再一层层穿出来（... → parameter → template）。这就是洋葱模型。

💡
这是 Web 框架的通用思想

请求一层层穿进去、响应一层层穿出来——Express、Koa、Hono 这些Web 框架全都这么干。RSSHub 用的是 Hono。学会这套思路，你看任何一个现代 Web 服务都能秒懂它怎么运转。

这意味着每一层中间件都有「两次机会」：请求穿过它时干一次活（比如 accessControl 查钥匙），响应穿回来时还能再干一次活（比如 template 渲染、header 设置 ETag）。出问题的时候，先想清楚是「进去时」还是「出来时」出的问题，你就锁定了一半的代码范围。

动手排个错 · 三道场景题

这三题考的都是「定位问题在哪个工位」——这是你跟 AI 排错时最值钱的能力。

Q1（debugging）你部署的 RSSHub 设了 ACCESS_KEY，结果阅读器订阅报 403 错误。最可能卡在哪一站？

Q2（概念）同一个订阅源，第一次打开很慢、第二次打开很快。为什么？

Q3（architecture）为什么 handler 只返回一个数据对象、不自己生成 RSS？
