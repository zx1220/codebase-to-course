数据变 RSS · 渲染输出的魔法

同一个数据对象，三种摆盘方式——这一站叫 template。

一个问题：handler 从不碰 XML，那 RSS 是哪来的？

前面模块你看到的 handler，自始至终只返回一个数据对象，从不碰 XML。

那这个数据对象是怎么「变成」阅读器能认的 RSS 的？秘密在流水线最后一站——一个叫 template 的渲染中间件。而且它不止会一种摆盘。

🍽️
同一个菜，三种摆盘

handler 端上来的是一盘「半成品」——一个数据对象 { title, link, item }。但阅读器们口味不同：有的只吃 RSS，有的爱吃 Atom，有的要 JSON。template 就像会三种摆盘手艺的厨师，同一锅菜按你的口味摆成不同样子端上桌。

点下面的 tab：同一份数据，三种长相

下面这三种格式，背后是同一个数据对象（某 UP 主的动态）。点 tab 切换，亲眼看看「摆盘」的区别。

<!-- ?format=rss （默认，不加也行）-->
<?xml version="1.0" encoding="UTF-8"?>
<rss version="2.0">
  <channel>
    <title>某UP主的动态</title>
    <link>https://bilibili.com/...</link>
    <item>
      <title>新视频</title>
      <link>https://b23.tv/...</link>
      <pubDate>Mon, 13 Jul 2026 10:00:00 GMT</pubDate>
    </item>
  </channel>
</rss>
<!-- ?format=atom -->
<?xml version="1.0" encoding="UTF-8"?>
<feed xmlns="http://www.w3.org/2005/Atom">
  <title>某UP主的动态</title>
  <link href="https://bilibili.com/..."/>
  <entry>
    <title>新视频</title>
    <link href="https://b23.tv/..."/>
    <updated>2026-07-13T10:00:00Z</updated>
  </entry>
</feed>
// ?format=json
{
  "version": "https://jsonfeed.org/version/1.1",
  "title": "某UP主的动态",
  "items": [
    {
      "title": "新视频",
      "url": "https://b23.tv/...",
      "date_published": "2026-07-13T10:00:00Z"
    }
  ]
}

三种长相，菜是同一道——区别只是「标签叫什么」和「用尖括号还是花括号」。厨师（template）按你 URL 里写的口味上菜。

1
不加任何参数

默认走 RSS 分支，端出来的是 <rss><channel><item> 这种 XML。

2
URL 后加 ?format=atom

走 Atom 分支，端出来的是 <feed><entry> 这种 XML。

3
URL 后加 ?format=json

走 JSON 分支，端出来的是花括号格式的 JSON Feed，程序最爱。

厨师怎么决定摆哪种盘？看 URL 里的 ?format=

这段是 template 中间件的核心。左边是真实代码，右边是逐句翻译——同一个 result 数据对象，喂给不同的渲染器。

CODE 
    switch (outputType) {
        case 'ums':
        case 'rss3':
            return ctx.json(rss3(result));
        case 'json':
            ctx.header('Content-Type', 'application/feed+json; charset=UTF-8');
            return ctx.body(json(result));
        case 'atom':
            return ctx.render(<Atom data={result} />);
        default:
            return ctx.render(<RSS data={result} />);
    }
中文翻译

开一个多路开关，根据 outputType 决定走哪条路——它就是用户在 URL 里写的 ?format=。

如果写的是 rss3，把数据交给 rss3() 函数转成 JSON 返回（一种特殊格式）。

如果写的是 json：先设一个 Content-Type 告诉对方「这是 JSON」，再把数据交给 json() 渲染。

如果写的是 atom，把数据塞进一个叫 <Atom> 的组件去渲染。

default 是「以上都不是」的兜底——默认走 RSS。所以不加 ?format= 时，你拿到的就是 RSS。

注意一个细节：所有分支用的都是同一个 result。数据没变，变的只是「把它喂给哪个渲染器」。这就是「同数据多视图」。

更妙的：RSS 居然是用 JSX「搭」出来的

你可能以为 XML 是一行行字符串拼出来的。错——RSSHub 用 JSX 把 XML 标签当成组件来搭，像拼积木。左边是真实代码（lib/views/rss.tsx）。

CODE 
const RSS: FC<{ data: Data }> = ({ data }) => {
    const hasItunes = data.itunes_author || data.itunes_category
        || (data.item && data.item.some((i) => i.itunes_item_image || i.itunes_duration));
    const hasMedia = data.item?.some((i) => i.media);
    const isTelegramLink = data.link?.startsWith('https://t.me/s/');

    return (
        <rss xmlns:atom="http://www.w3.org/2005/Atom"
             xmlns:itunes={hasItunes ? 'http://...dtd' : undefined}
             version="2.0">
            <channel>
                <title>{data.title || 'RSSHub'}</title>
                <link>{data.link || 'https://docs.rsshub.app'}</link>
中文翻译

定义一个叫 RSS 的组件，它接收 data 作为输入（就是 handler 端上来的那盘半成品）。

先做几个判断：这批数据里有没有 iTunes 播客字段？有没有媒体（media）？链接是不是 Telegram？

这些判断用来决定要不要在 XML 里加额外的命名空间标签——按需启用，不是死写。

然后 return 一段 JSX：直接写 <rss>、<channel>、<title> 这些 XML 标签，跟写 HTML 一模一样。

花括号 {data.title} 是「把数据塞进来」的语法——标题来自数据对象，没有就用默认值 'RSSHub'。

那一条条内容是怎么变成 XML 的？下面这段是 rss.tsx 的下一节——用 map 把数组「展开」成一堆 <item> 标签：

CODE 
                {data.item?.map((item) => (
                    <item>
                        <title>{item.title}</title>
                        <description>{item.description}</description>
                        <link>{item.link}</link>
                        <guid isPermaLink="false">{item.guid || item.link || item.title}</guid>
                        {item.pubDate && <pubDate>{item.pubDate}</pubDate>}
                        {item.author && <author>{item.author}</author>}
                        {item.image && <enclosure url={item.image} type="image/jpeg" />}
中文翻译

对数据里的 item 数组做 map——「数组里每一条，都给我变成一个 <item> 标签」。

每条内容的标题、描述、链接，分别塞进对应的子标签。

guid 是这条内容的唯一 ID，没有就用链接或标题顶上。

{item.pubDate && <pubDate>...</pubDate>} 是个聪明写法：「如果有发布日期，才输出这个标签；没有就别输出」。

作者、配图同理——有才输出。所以最终 XML 是按数据动态拼出来的，不是固定模板。

🧩
把 XML 当积木搭

JSX 让 XML 标签变成了可以拼接、可以判断、可以循环的「积木」。同一个思想：网页能用 JSX 搭，配置文件、XML 订阅源也能用 JSX 搭。这就是「模板」的现代写法。

三种格式，各有什么用？

阅读器世界没有「唯一标准」，所以 RSSHub 三种都给。下面是它们各自的性格：

📰

RSS 2.0

最通用、最老牌。几乎所有阅读器都吃。RSSHub 的默认输出就是它。

⚡

Atom

更现代、更规范。日期格式、必填字段都更严谨。想用它，URL 加 ?format=atom。

{ }

JSON Feed

不是 XML，是给程序读的 JSON。代码解析最省事。想用它，URL 加 ?format=json。

怎么切换？全靠 URL 里的查询参数 ?format=。同一个源，加不同后缀，拿不同格式。菜没变，摆盘变了。

背后的大智慧：把数据和展示分开

handler 只管「抓数据」，template 只管「摆盘」——这种分工有个大名堂。

💡
模型-视图思想

把「数据」（模型 M）和「展示」（视图 V）分开来写。这是从桌面软件到 Web 到现在所有界面设计的通用大智慧。RSSHub 里：handler = 模型（抓数据），template = 视图（摆盘）。

好处很实在：想加一种新输出格式？写个新视图就行，handler 一行都不用改。想换个数据源？换 handler，视图照常工作。这就是「关注点分离」。

以后你跟 AI 聊「把数据和展示分开」「我要加一种新的输出格式」，脑子里就想到 RSSHub 这套 handler / template 的分工——你已经掌握了一个能用一辈子的设计思想。
