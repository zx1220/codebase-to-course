一条订阅源的诞生 · 路由文件解剖

看懂一个文件，就看懂了 RSSHub 八成的代码。

RSSHub 的「灵魂」长什么样？

上一模块我们看到 /bilibili/user/dynamic/2267573 能订阅一个 B站 UP 主。但 RSSHub 是怎么知道「遇到 bilibili 就调 B站、遇到 weibo 就调微博」的？

答案藏在一种叫路由文件的东西里——它就是 RSSHub 的灵魂。

🍽️
核心比喻：外卖菜单 + 后厨配方

把整个 lib/routes/ 想象成一条美食街。每个文件夹就是「一家餐厅」（比如 B站、微博、GitHub），文件夹里每个 .ts 文件就是菜单上的一道菜。菜单上写这道菜叫什么、长什么样；后厨配方（handler 函数）写怎么买菜、怎么炒、怎么装盘。

这条街上有 1600 多家「餐厅」

RSSHub 用一个极简约定组织了 1600+ 个网站源：一个文件夹 = 一个网站，一个 .ts 文件 = 一条订阅源。

lib/routes/ 这条「美食街」——所有网站源都在这里
bilibili/ 「B站这家餐厅」(namespace)
namespace.ts 这家店的「身份证」
article.ts 一道菜：UP主图文
dynamic.ts 一道菜：UP主动态
video.ts 一道菜：视频
… 50 多个文件 = 50 多道菜
weibo/ 「微博这家餐厅」
github/ 「GitHub这家餐厅」
… 1600+ 个文件夹

每个餐厅还有一个 namespace.ts——它的身份证。

先看「身份证」：namespace.ts

每个网站文件夹里都有一个 namespace.ts，短短几行，只声明这家餐厅是谁。

CODE 
import type { Namespace } from '@/types';

export const namespace: Namespace = {
    name: '哔哩哔哩 bilibili',
    url: 'www.bilibili.com',
    lang: 'zh-CN',
};
大白话翻译

引入一个「类型模板」，告诉编辑器「我要写的是一份身份证」。

name 是显示名——用户在文档里看到的中文+英文名。

url 是目标网站地址——这家餐厅对应的「菜市场」。

lang 是语言——B站是中文站，所以标 zh-CN。

就这样。身份证只管「我是谁」，不管怎么做菜。

再看「菜单」：route 对象声明

每个 .ts 文件都 export 一个 route 对象，声明这条源「负责什么 URL、叫什么名字、谁在维护」。

CODE 
export const route: Route = {
    path: '/user/article/:uid',
    categories: ['social-media'],
    example: '/bilibili/user/article/334958638',
    parameters: { uid: '用户 id, 可在 UP 主主页中找到' },
    features: {
        requireConfig: false,
        requirePuppeteer: false,
        antiCrawler: false,
        supportBT: false,
        supportPodcast: false,
        supportScihub: false,
    },
    radar: [
        {
            source: ['space.bilibili.com/:uid'],
        },
    ],
    name: 'UP 主图文',
    maintainers: ['lengthmin', 'Qixingchen', 'hyoban'],
    handler,
};
大白话翻译

path 是「我负责哪种地址」。:uid 是一个参数占位符，谁填什么就抓谁。

example 是一个能直接用的示例地址，会显示在文档里供人复制。

parameters 解释每个参数是什么意思——给用户看的人话说明。

features 是一组开关：要不要配置、要不要开浏览器、会不会被反爬……

name 是这条源的人话名字（「UP 主图文」），maintainers 是负责这个文件的维护者。

最后一行 handler 指向真正干活的函数——下一幕登场。

后厨配方：handler 函数在干什么

这是同一个 article.ts 里的 handler。它干三件事：① 拿到 API JSON 数据、② 解析每一篇文章、③ 打包返回。

CODE 
async function handler(ctx) {
    const uid = ctx.req.param('uid');
    const name = await cache.getUsernameFromUID(uid);
    const response = await got({
        method: 'get',
        url: `https://api.bilibili.com/x/polymer/web-dynamic/v1/opus/feed/space?host_mid=${uid}`,
        headers: {
            Referer: `https://space.bilibili.com/${uid}/article`,
        },
    });
    const data = response.data.data;
    const title = `${name} 的 bilibili 图文`;
        // ……中间省略：用 load() 解析每篇文章网页、提取正文和日期……
    return {
        title,
        link,
        description,
        item,
    };
}
大白话翻译

这是一个异步函数，ctx 是这次请求的「上下文」。

先从 URL 里取出 uid，再查缓存拿用户名。

got(...) 是HTTP 客户端，RSSHub 派它去敲 B站 的接口拿数据。

中间省略的部分：用 load()（cheerio）配合 CSS 选择器）解析每篇文章，用 cookie 通过反爬。

Promise.all 是「同时跑多个任务、等它们全部完成」的写法——比如同时解析 20 篇文章。

注意最后这几行：它返回的是一个纯数据对象，不是 RSS，不是 XML。

最关键的设计：handler 只返回「数据」

handler 不碰 RSS XML，不写标签，不管输出长什么样——它只吐出一个数据对象。这是整个 RSSHub 最聪明的地方。

CODE 
return {
    title,
    link,
    description,
    item,
};
大白话翻译

title 是这整个订阅源的名字（「某某 的 bilibili 图文」）。

link 是回链——点进去能去到 B站主页。

description 是一句话简介。

item 是一个数组，装着每一条内容（每篇文章一个对象）。

就这些。handler 完全不知道 RSS 长什么样——RSS 的拼接由别人管。这就是 5000+ 路由文件能共用一套渲染引擎的根本原因。

💡
大智慧：分离关注点 (Separation of Concerns)

handler 只管「去哪拿数据、拿什么」，RSS 长什么样由另一个渲染引擎负责。抓取逻辑和输出格式彻底解耦——同一套抓取代码能同时输出 RSS / Atom / JSON。这是软件工程里最重要的思想之一：让每个部分只干一件事。

以后你想「给某个还没收录的网站加一个源」，或者想让 AI「仿照这个结构写一个抓取器」，你现在都能精确描述需求了。

结构就是契约

一个 path、一个 handler、返回 { title, link, description, item }。RSSHub 1600+ 个源全遵守这个约定。

🤖

能跟 AI 说清楚

你可以说「仿照 lib/routes/bilibili/article.ts 写一个抓 XX 网站的源」，AI 就知道该输出什么结构。

🔍

能判断对错

如果 AI 给你的 handler 在自己拼 XML、自己 ctx.body(...)，那它就写错了——抓住这一点，你就成了审查者。
