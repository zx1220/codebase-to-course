这是 handler 吐出的统一数据对象——整个 RSSHub 流水线的「标准货物」。

handler 造它（模块 2），cache 存它（模块 5）。

parameter 美化它（模块 3），template 渲染它（模块 4）。

四个字段，就是五个模块之间交接的「提货单」。谁都不关心别人怎么干，只认这个对象。

RSSHub 为什么不崩溃？三句哲学

1600+ 个源、社区维护，却没乱成一锅粥。秘密就藏在这三个设计选择里——它们也是你能搬走的核心收获。

📁

约定优于配置

文件夹 = 网站，文件 = 源。1600+ 源靠这套文件系统约定组织，不用维护中央路由表。

你能怎么用：自己的项目也定死一条「放哪=是什么」的规矩，省掉一堆 if/else。

🔀

关注点分离

handler 只抓数据，缓存 / 美化 / 渲染全交给中间件。

你能怎么用：写函数时问自己「这段是不是在干两件事」——是，就拆成两个。

🛡️

用聪明工程保护自己

单飞缓存防惊群，原子操作防竞态。

你能怎么用：凡是「很多人同时抢同一份资源」的地方，都想想「谁能帮我把并发收敛成一个」。

好架构的本质

💡
aha！这就是一切的秘密

好架构的本质，是「让简单的部分保持简单，让复杂的部分各司其职」。RSSHub 能靠社区维护 插件化地长出 1600+ 个源却不崩溃，靠的不是某个天才，而是这套约定和分工。

恭喜你走完了 RSSHub 的每一个核心部分。现在你拥有了读、理解、指挥这类项目的能力——下次遇到任何「抓取 + 转换 + 服务」型的系统，你心里已经有了一张图，知道该往哪儿看、该跟 AI 怎么说。这套架构直觉，比记任何一行代码都值钱。
