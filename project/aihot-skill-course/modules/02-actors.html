把「用户 / AI 助手 / SKILL.md / aihot API」当四个有性格的角色，戏就好看懂了

演员表：四个角色，各司其职

一场 AI 资讯查询不是「一个人在干活」——是四个角色在接力。记住这四张脸，后面所有事都是他们之间的对手戏。

🙋

用户

说人话的那个人。只会用中文提需求，看不懂参数名，要的是「一份能直接读的简报」。

🤖

AI 助手

聪明的执行者。会读说明书、会拼命令、会排版——但本身没有任何今日资讯，必须现场去查。

📜

SKILL.md

一张静默的便签。不会主动说话，只在被 AI 翻开时，把「该走哪个接口、怎么排版」的规矩亮出来。

🌐

aihot API

真正的数据仓库。住在网站上，收请求、吐 JSON。所有今天的新闻都从它这里出。

SKILL.md 是「沉默的配角」

注意 SKILL.md 从头到尾没有主动发过一条消息——它只在 AI 翻开它时亮出规矩，AI 读完就合上。这是 Skill 这种扩展形态的本质：它是被查阅的说明书，不是常驻的后台服务。理解这一点，你就明白为什么 SKILL.md 里写得越清楚，AI 表现越好——因为它只有这一次「被读到」的机会。

他们之间用什么「语言」对话

四个角色用三种不同的语言交流。搞清楚谁说什么话，你就掌握了整个系统的协议。

1
用户 ⇄ AI 助手：自然语言

中文大白话，进和出都是。「今天 AI 圈有啥」进去，「AI HOT — 最近 30 条精选」出来。中间一切技术细节都对用户隐形。

2
AI 助手 ⇄ SKILL.md：markdown 规矩

AI 读的是这份文档的正文——表格、curl 示例、「不要做」清单。这是一场单向阅读：AI 读，SKILL.md 不回话。

3
AI 助手 ⇄ aihot API：HTTP + JSON

AI 拼 curl 命令发出去，API 回 HTTP 状态码 + JSON 正文。请求里塞参数（mode、since、category），响应里塞数据条目。这是唯一一段机器对机器的对话。

🔍
为什么这个分层很值钱

用户永远不必学 curl 和 JSON；AI 助手永远不必自己开发爬虫；aihot 网站永远不必关心用户长什么样。每层只做自己擅长的事，靠明确的接口对接。这种「分层 + 协议」的思路，是几乎所有软件系统的底层骨架——你以后看任何项目，都可以先问一句：「它分了几层？层与层之间用什么语言说话？」
