触发：description 的魔法

整个系统里最关键、也最容易被忽视的一个字段。它写得好不好，直接决定技能"装了等于没装"还是"指哪打哪"。

回顾一下：Claude 怎么决定用不用你的技能？

还记得 Module 1 的那张流程图吗？Claude 决策时，唯一能看到的就是每个技能的 description。

💡
这是整个系统的咽喉要道

name 只是身份证号，SKILL.md 正文它还看不到。Claude 判断"这个任务要不要调某个技能"，完全依赖 description 这几十上百个字。description 写砸了，再牛的技能也永远触发不了——等于白装。

仓库里直接点明了这件事的分量：

skill-creator/SKILL.md 

**description**: When to trigger,
what it does. This is the
primary triggering mechanism
- include both what the skill
does AND specific contexts for
when to use it. All "when to use"
info goes here, not in the body.
逐行翻译

description：什么时候触发、做什么事。

这是首要的触发机制——

要同时写清楚"技能能干啥"和"什么场景下该用它"。

所有"何时使用"的信息……

都放这里，别放到正文里（正文触发时才看，太晚了）。

反直觉的建议：要"强势"一点

这里有个特别实在的洞察。Claude 有个通病——该用技能时常常不敢用（官方叫"undertrigger"，触发不足）。怎么治？看原文：

skill-creator/SKILL.md 

Note: currently Claude has a
tendency to "undertrigger"
skills -- to not use them when
they would be useful. To combat
this, please make the skill
descriptions a little bit
"pushy".
逐行翻译

注意：现在的 Claude 有个倾向……

会"触发不足"——

明明该用某个技能，它却不用。

为了对付这个毛病……

请把技能的描述写得稍微"强势"一点。

原文还直接给了个改写示范，非常值得揣摩：

改写示范 

# 原版（太含蓄）：
"How to build a simple fast
 dashboard to display internal
 Anthropic data."

# 改写版（pushy）：
"How to build a simple fast
 dashboard... Make sure to use
 this skill whenever the user
 mentions dashboards, data
 visualization, internal metrics,
 or wants to display any kind of
 company data, even if they do not
 explicitly ask for a dashboard."
对比解读

原版只是客观描述能干啥。

问题在于：用户可能说"我想看看销售数据"，没提"dashboard"这个词——原版就不会触发。

改写版主动列举了用户可能说的各种说法。

还专门加了一句"哪怕没明说要 dashboard，只要有这些迹象就用我"。

这就是"pushy"——不是无礼，而是把触发条件铺得足够广，把犹豫的 Claude 推一把。

看仓库里的"教科书级"写法

这个仓库里的 description 本身就是范本。挑两个对比着看——先看一个普通但合格的：

skills/mcp-builder/SKILL.md 

description: Guide for creating
  high-quality MCP servers that
  enable LLMs to interact with
  external services through
  well-designed tools. Use when
  building MCP servers to
  integrate APIs or services,
  whether in Python (FastMCP)
  or Node/TypeScript (MCP SDK).
拆解它的套路

第一句：这是什么（造 MCP 服务的指南）。

中间：价值（让大模型能跟外部服务交互）。

最后："Use when"——明确触发时机。

还贴心地列了技术栈（Python / TypeScript），覆盖不同说法。

再看一个把 pushy 发挥到极致的——仓库里的 claude-api 技能，它的 description 简直像一份"使用说明书"：

skills/claude-api/SKILL.md 

description: |-
  TRIGGER — read BEFORE opening
  the target file; do not skip
  because it "looks like a
  one-liner" — whenever: the
  prompt names Claude/Anthropic...
  OR the task is LLM-shaped with
  provider unstated (agent/MCP/
  tool-definition/multi-agent/RAG
  ...).
  SKIP only when another provider
  is being worked on...
它强在哪

开头就喊"TRIGGER"——当命令用。

预防性地说"别因为文件看着简单就跳过我"——堵住 AI 的偷懒借口。

疯狂列举触发词：Claude、Anthropic、agent、MCP、RAG……

还写了反向条件："SKIP only when"——什么时候不要触发。

正反两面都堵死了，AI 几乎没有误判空间。这是 description 写作的天花板。

description 的两条硬规矩

写 description 不能放飞。校验脚本 quick_validate.py 卡了两条硬限制，违反就打包失败：

📏

最多 1024 个字符

推起来要够广，但不能啰嗦到撑爆第一级（永远在脑中的元数据）。在"覆盖足够多触发词"和"保持精炼"之间找平衡。

🚫

不能有尖括号 < >

因为 description 会被当成纯文本处理，尖括号会被误读成 HTML/XML 标签而惹乱子。想强调就用引号或大写，别用 <这样>。

对应的校验代码很直白：

quick_validate.py 

# Check for angle brackets
if '<' in description
  or '>' in description:
  return False,
    "Description cannot contain"
    "angle brackets"

# Check description length
if len(description) > 1024:
  return False,
    f"...Maximum is 1024..."
逐行翻译

检查 description 里有没有尖括号。

只要有一个 < 或 >……

校验失败："不能包含尖括号"。

再检查长度。

超过 1024 个字符……

同样失败，上限就是 1024。

但别忘了：AI 是"按需"才查技能的

有个特别重要的细节，原文专门强调过。它会影响你怎么设计测试用例：

skill-creator/SKILL.md 

Claude only consults skills for
tasks it cannot easily handle on
its own -- simple, one-step
queries like "read this PDF" may
not trigger a skill even if the
description matches perfectly.
逐行翻译

Claude 只在遇到自己搞不定的任务时，才会去翻技能。

那种简单的一步任务……

比如"读一下这个 PDF"……

可能根本不会触发技能……

哪怕 description 写得完美匹配——因为它觉得自己直接就能干。

⚠️
实战影响：测试技能时别用太简单的任务

你想验证"PDF 技能能不能触发"，如果只输入"读一下 a.pdf"，可能根本不触发——不是技能坏了，是任务太简单 Claude 觉得自己能搞定。要用复杂、多步、专业的真实任务来测，比如"提取这份合同的违约条款并按风险排序"。这也是后面 Module 5 会讲的"评测"的关键。

注意"训练集 vs 验证集"的智慧

为什么要分两份数据？因为如果只在一批问题上反复优化，AI 可能只是背会了那批问题（overfitting，过拟合），换个说法就又不灵了。留一份"从没见过的"验证集，才能确认它是真学会了而不是死记硬背。这个思想在所有 AI 训练里都通用。
