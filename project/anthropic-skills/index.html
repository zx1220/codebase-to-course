解密 Agent Skills
01

什么是 Skill？

你每天都在用 AI 做事——但你有没有想过，能不能给它装一个"专门技能"？

先想一个场景

想象一下：你让 AI 帮你处理一个 Excel 表格。可它根本不懂你们公司那一套特殊的"利润率要按蓝色、年份不带千位分隔符"的规矩。每次都要重新解释一遍，对吧？

如果能一次性把这些规矩教会它，以后它每次碰到表格都自动照办——那该多省心。

💡
这就是 Skill 想解决的问题

Skill 是一个装满说明书、脚本和资源的文件夹，让 Claude（以及其他 AI）在碰到特定任务时"自动加载"这些知识，不用你每次重复啰嗦。

提示：文中的 虚线词语 都可以悬停/点击查看大白话解释。

用最直白的话说

官方的定义是这样写的：

README.md 

Skills are folders of instructions,
scripts, and resources that Claude
loads dynamically to improve performance
on specialized tasks.
大白话翻译

Skill 就是一个装着说明书的文件夹……

里面还可能有脚本（能直接运行的代码）和各种资源（比如模板、字体）……

Claude 会根据需要动态加载它——用到时才翻开，不用时收起来。

目的只有一个：让它在某个专业任务上做得更好、更稳定。

🎯
打一个比方：技能包

想象 Claude 是个聪明的实习生。它什么都能学，但你没教过的规矩它就不知道。一个 Skill 就像是你递给它的一份"岗位手册"——只在这个岗位需要时才拿出来看，平时不占它脑子。

一个真实的 Skill 长什么样？

这个仓库里就有 17 个现成的 Skill。咱们挑一个最直观的看看它的"身份证"——也就是它最核心的那个文件 SKILL.md：

下面这段是 YAML 写的"配置区"，夹在两组三道杠 --- 中间：

skills/pdf/SKILL.md 

---
name: pdf
description: Use this skill whenever the
  user wants to do anything with PDF
  files. This includes reading or
  extracting text...
---

# PDF 处理指南
（后面是详细的操作步骤）
逐行翻译

这三道杠 --- 是一个分隔标记，告诉 AI "上面这部分是配置信息"。

name：这个技能叫 pdf，是它的唯一名字。

description：这段话才是真正的"触发开关"——它告诉 Claude 什么时候该用这个技能。

意思是："只要用户想对 PDF 文件做任何事，就用我。"

第二个 --- 表示配置结束。

下面就是真正的"教学内容"了。

就这么简单。一个文件夹、一个 SKILL.md 文件，就是一个完整的 Skill。

它到底解决什么问题？

本质上是两个矛盾：

🧠

矛盾一：AI 的脑容量有限

你没法把世界上所有的规矩一次性塞进对话里。AI 每次"记不住"那么长的上下文。

🔄

矛盾二：你不想重复劳动

每次开新对话都要重新解释一遍"我们公司表格怎么排版"，太累，还容易出错。

Skill 的解法是"按需加载"：

  • ✅ 把专业知识打包进文件夹，一次写好
  • ✅ AI 平时只看它的名字和简介（省脑容量）
  • ✅ 真要用到了，自动翻开详细说明
  • ✅ 用完就收起来，不干扰其他任务

关键洞察

Claude 自己决定要不要用某个 Skill——你不需要手动"调用"。它靠的就是那个 description 字段。写得好，它就准；写得差，它就漏。这就是为什么后面我们会专门讲怎么写好这个字段。

02

一个 Skill 的解剖结构

剥开一个 Skill 文件夹，看看里面到底装了哪些零件，各管什么用。

从一个"最小可用"的 Skill 开始

这是仓库里自带的模板（template），一个 Skill 最少需要这些东西：

template/SKILL.md（原文） 

---
name: template-skill
description: Replace with description
  of the skill and when Claude
  should use it.
---

# Insert instructions below
逐行翻译

--- 标记"配置区"开始。

name：技能的唯一 ID，只能用小写字母、数字、连字符（kebab-case）。

description：这是触发开关——告诉 Claude 什么时候该用它。

--- 配置区结束。

下面用 Markdown 写真正的"教学步骤"。

💡
两个必填字段，缺一不可

整个 Skill 系统只认 name 和 description 这两个字段是必须的。其他全是可选。记住这点——它会帮你理解为什么 description 那么关键（Module 4 会专门讲）。

完整的 Skill 长什么样？

当任务变复杂，一个 Skill 就会"长"出更多文件夹。这是仓库里 skill-creator 总结的标准结构：

skill-name/ 整个技能的根文件夹
SKILL.md ★ 必需。配置 + 主说明书
scripts/ 可执行的代码——干"确定性强"的活
references/ 文档，按需才读（省脑容量）
assets/ 输出时要用的素材：模板、图标、字体
evals/ 测试用例，用来验证技能好不好使

注意：只有 SKILL.md 是必需的，其余四个文件夹都是按需添加。简单技能啥都不用加。

scripts / references / assets，有啥区别？

这三个可选文件夹最容易搞混。它们的核心区别在于"谁来执行"和"什么时候被用到"：

⚙️

scripts/

代码亲自干活。适合确定性强、重复的任务——比如"把 PDF 转成图片"。Claude 调用它运行，结果可信。

📚

references/

给 Claude 读的说明书。适合需要判断、灵活应变的场景——比如"各种云平台的部署差异"。Claude 读进脑子的文字。

🎨

assets/

现成的素材。Claude 不需要"理解"它，直接拿来用——比如公司 logo、PPT 模板、字体文件。

🎯
判断技巧：问自己一个问题

"这事是一步一步死步骤吗？" → 用 scripts。"这事需要看情况判断吗？" → 用 references。"这是个现成文件吗？" → 用 assets。

配置区（frontmatter）能写哪些字段？

文件顶部那段夹在三道杠之间的配置区，学名叫 frontmatter。仓库里有个 quick_validate.py 校验脚本，它白纸黑字规定了哪些字段合法。看它的代码就知道规则：

skill-creator/scripts/quick_validate.py 

# Define allowed properties
ALLOWED_PROPERTIES = {
  'name', 'description',
  'license', 'allowed-tools',
  'metadata', 'compatibility'
}

# Check for unexpected properties
unexpected_keys =
  set(frontmatter.keys())
  - ALLOWED_PROPERTIES
if unexpected_keys:
  return False,
    f"Unexpected key(s)..."
逐行翻译

这是脚本里定义的合法字段白名单。

name 和 description——必填，前面讲过。

license（许可证）、allowed-tools（允许用的工具）——可选。

metadata（元数据）、compatibility（兼容性）——可选。

脚本把用户写的字段跟白名单做减法。

只要有多余的字段（比如你手滑写了 nmae）……

校验直接失败，打包都过不了。

⚠️
常见的坑：字段名写错

校验对字段名是严格的。你写 desciption（拼错）或 tools（简写）都会被拒。这是好事——它强迫你写规范，避免 AI 加载时困惑。

03

渐进式披露

Skill 系统最聪明的设计：像洋葱一样一层层剥开，用到哪层翻哪层。

先理解一个根本限制

AI 有个绕不开的物理限制：上下文窗口。

如果把所有技能的全部说明书一次性塞给它，桌子立刻爆满——它反而什么都做不好。

💡
所以 Skill 系统的核心设计问题

怎么做到"既装得下海量专业知识，又不撑爆脑容量"？答案就是仓库里反复强调的设计哲学：渐进式披露（Progressive Disclosure）。

三层加载，各管一摊

这是 skill-creator 里白纸黑字写的官方设计。看原文怎么描述这套机制（context 在这里就是"AI 此刻脑子里装的东西"）：

skill-creator/SKILL.md 

#### Progressive Disclosure

Skills use a three-level
loading system:
1. Metadata (name + description)
   - Always in context (~100 words)
2. SKILL.md body
   - In context whenever skill triggers
   - (<500 lines ideal)
3. Bundled resources
   - As needed (unlimited,
   scripts can execute w/o loading)
逐行翻译

小标题：渐进式披露。

技能用一套三级加载系统。

第一级：元数据（名字 + 简介）。

这个永远在 Claude 脑子里，大概才 100 个词——所以再省不过了。

第二级：SKILL.md 正文。

只有当技能被触发时才整篇加载进来。

理想情况控制在 500 行以内。

第三级：捆绑资源（scripts/references/assets）。

按需才读，不限大小——而且脚本能直接跑，根本不用读进脑子！

用"图书馆"理解这三层

想象 Claude 是个图书管理员，面前是一座巨大的图书馆。这套三级系统就像图书馆的检索效率设计：

📇

第一级 · 卡片目录

永远摊在桌面。每本书只有一张索引卡（书名+一句话简介）。管理员扫一眼就知道哪本书可能相关——但书的细节一点没读。

📖

第二级 · 翻开那本书

确认相关了才取下来读。读的是书的正文（SKILL.md）。这一步才真正"占脑容量"，所以要克制——500 行内。

🗄️

第三级 · 查阅书后附录

遇到具体难题才去翻。书的附录、参考文献（references）无限多也不怕，用到哪本翻哪本。脚本更妙——直接让机器替你跑，自己都不用读。

🎯
这套设计的精妙之处

100 本书的卡片目录只占一张桌面的角落，但能让管理员瞬间定位到任何一本。Skill 系统也是：你装 50 个技能，第一级才占 5000 词——而真用起来，每次只深挖其中一两个。

"SKILL.md 控制在 500 行"——为什么？

这条规则不是拍脑袋定的。它背后有个朴素的道理，原文是这么解释的：

skill-creator/SKILL.md 

**Key patterns:**
- Keep SKILL.md under 500 lines;
  if you are approaching
  this limit, add an additional
  layer of hierarchy along
  with clear pointers about
  where the model should go
  next to follow up.

- Reference files clearly from
  SKILL.md with guidance on
  when to read them
逐行翻译

关键模式：

把 SKILL.md 控制在 500 行以内。

如果你快超了……

那就再加一层结构（拆出 references 文件）……

并且写清楚"接下来该去哪读"的指引。

在 SKILL.md 里要明确引用那些外部文件……

并告诉模型"什么时候"该去读它们。

这就引出了一条实战铁律：SKILL.md 是"目录 + 总纲"，不是"全书"。细节往 references 里塞，主文件只留主干和"路标"。

一个高级技巧：按"域"分文件

当技能要支持好几个不同的东西（比如部署到 AWS、GCP、Azure 三朵云），仓库推荐这样组织——主文件只做调度，细节分文件存：

skill-creator/SKILL.md（分域组织） 

**Domain organization**: When a
skill supports multiple
domains/frameworks, organize
by variant:

cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md

Claude reads only the relevant
reference file.
逐行翻译

分域组织：当一个技能……

要支持多个"领域/框架"时，按"变体"来组织。

假设有个"云部署"技能，目录长这样：

SKILL.md 只负责"整体流程 + 选哪个云"。

具体的部署细节拆进 references 文件夹……

AWS 的归 aws.md，GCP 的归 gcp.md，Azure 的归 azure.md。

结果是：Claude 只读它真正需要的那一个文件。你说要部署到 GCP，它绝不碰 aws.md——又省一大块脑容量。

💡
这是给 AI 写说明书的通用智慧

无论是不是 Skill，给 AI 提供信息时，"分层 + 带路标"永远比"一锅端"好。AI 跟人一样——面对一本 5000 页的手册会懵，面对一份"目录+按需展开"的指南就能高效干活。这个原则你在指挥 AI 时随时能用上。

看仓库里的真实案例：mcp-builder

mcp-builder（教 AI 造 MCP 服务的技能）正是这么做的。它的 SKILL.md 主文件做调度，把 Python 和 TypeScript 两种语言的具体玩法拆进了 reference 文件夹：

mcp-builder/ 支持两种语言的复杂技能
SKILL.md 主流程 + "选哪种语言"的指引
reference/ 按需加载的深度文档
scripts/ 评测代码（不读，直接跑）

当你说"用 Python 写个 MCP 服务"，它只读 python_mcp_server.md；说 TypeScript，就读 node_mcp_server.md。两条线互不干扰，脑容量省一半。

🔍
小细节：reference 还是 references？

注意 mcp-builder 用的是 reference/（单数），而 skill-creator 规范里写的是 references/（复数）。文件夹名其实没有强制要求——关键是 SKILL.md 里要写清楚"去哪里读、什么时候读"。AI 看的是你的指引，不是文件夹名。

04

触发：description 的魔法

整个系统里最关键、也最容易被忽视的一个字段。它写得好不好，直接决定技能"装了等于没装"还是"指哪打哪"。

回顾一下：Claude 怎么决定用不用你的技能？

还记得 Module 1 的那张流程图吗？Claude 决策时，唯一能看到的就是每个技能的 description。

💡
这是整个系统的咽喉要道

name 只是身份证号，SKILL.md 正文它还看不到。Claude 判断"这个任务要不要调某个技能"，完全依赖 description 这几十上百个字。description 写砸了，再牛的技能也永远触发不了——等于白装。

仓库里直接点明了这件事的分量：

skill-creator/SKILL.md 

**description**: When to trigger,
what it does. This is the
primary triggering mechanism
- include both what the skill
does AND specific contexts for
when to use it. All "when to use"
info goes here, not in the body.
逐行翻译

description：什么时候触发、做什么事。

这是首要的触发机制——

要同时写清楚"技能能干啥"和"什么场景下该用它"。

所有"何时使用"的信息……

都放这里，别放到正文里（正文触发时才看，太晚了）。

反直觉的建议：要"强势"一点

这里有个特别实在的洞察。Claude 有个通病——该用技能时常常不敢用（官方叫"undertrigger"，触发不足）。怎么治？看原文：

skill-creator/SKILL.md 

Note: currently Claude has a
tendency to "undertrigger"
skills -- to not use them when
they would be useful. To combat
this, please make the skill
descriptions a little bit
"pushy".
逐行翻译

注意：现在的 Claude 有个倾向……

会"触发不足"——

明明该用某个技能，它却不用。

为了对付这个毛病……

请把技能的描述写得稍微"强势"一点。

原文还直接给了个改写示范，非常值得揣摩：

改写示范 

# 原版（太含蓄）：
"How to build a simple fast
 dashboard to display internal
 Anthropic data."

# 改写版（pushy）：
"How to build a simple fast
 dashboard... Make sure to use
 this skill whenever the user
 mentions dashboards, data
 visualization, internal metrics,
 or wants to display any kind of
 company data, even if they do not
 explicitly ask for a dashboard."
对比解读

原版只是客观描述能干啥。

问题在于：用户可能说"我想看看销售数据"，没提"dashboard"这个词——原版就不会触发。

改写版主动列举了用户可能说的各种说法。

还专门加了一句"哪怕没明说要 dashboard，只要有这些迹象就用我"。

这就是"pushy"——不是无礼，而是把触发条件铺得足够广，把犹豫的 Claude 推一把。

看仓库里的"教科书级"写法

这个仓库里的 description 本身就是范本。挑两个对比着看——先看一个普通但合格的：

description: Guide for creating

description 的两条硬规矩

写 description 不能放飞。校验脚本 quick_validate.py 卡了两条硬限制，违反就打包失败：

📏

最多 1024 个字符

推起来要够广，但不能啰嗦到撑爆第一级（永远在脑中的元数据）。在"覆盖足够多触发词"和"保持精炼"之间找平衡。

🚫

不能有尖括号 < >

因为 description 会被当成纯文本处理，尖括号会被误读成 HTML/XML 标签而惹乱子。想强调就用引号或大写，别用 <这样>。

对应的校验代码很直白：

quick_validate.py 

# Check for angle brackets
if '<' in description
  or '>' in description:
  return False,
    "Description cannot contain"
    "angle brackets"

# Check description length
if len(description) > 1024:
  return False,
    f"...Maximum is 1024..."
逐行翻译

检查 description 里有没有尖括号。

只要有一个 < 或 >……

校验失败："不能包含尖括号"。

再检查长度。

超过 1024 个字符……

同样失败，上限就是 1024。

创建与迭代循环

理论都懂了——那真要从零造一个技能，到底该走什么流程？仓库里的 skill-creator 给了一套成熟方法论。

先记住最重要的一句话

很多人以为"造技能"就是坐下来写一份完美的 SKILL.md。仓库里的 skill-creator 开篇就打破了这个幻想：

skill-creator/SKILL.md 

At a high level, the process of
creating a skill goes like this:

- Decide what you want it to do
- Write a draft of the skill
- Create a few test prompts and
  run claude-with-the-skill on them
- Evaluate the results (qual + quant)
- Rewrite based on feedback
- Repeat until satisfied
逐行翻译

造一个技能，宏观上是这么个流程：

先想清楚要它干啥。

写一版草稿（注意：是草稿，不是终稿）。

准备几个测试问题，然后带着技能跑一遍。

评估结果（定性看质量 + 定量看指标）。

根据反馈重写。

循环，直到满意。

💡
这跟写代码、写文章是同一个道理

没有人第一稿就写对。技能也是"草稿 → 测 → 改 → 再测"打磨出来的。接受这一点，你就不会因为第一版不完美而沮丧——因为本来就不该完美。关键是把循环转起来。

写作心法：讲道理，别下命令

新手写技能容易犯一个错：通篇"MUST"、"NEVER"、"ALWAYS"，像在训狗。仓库明确反对这种写法。看原文：

skill-creator/SKILL.md 

Explain the why. Try hard to
explain the why behind everything.
Today's LLMs are smart. They have
good theory of mind... Even if
feedback is terse, try to actually
understand the task and transmit
this understanding into instructions.

If you find yourself writing ALWAYS
or NEVER in all caps... that is a
yellow flag -- reframe and explain
the reasoning.
逐行翻译

解释"为什么"。尽力把每条指令背后的原因讲清楚。

今天的大模型很聪明，有不错的"心智理论"（能揣摩意图）。

哪怕用户的反馈很简短，也要真正去理解任务……

然后把这份理解传递进指令里。

如果你发现自己又在写大写的 ALWAYS / NEVER……

那是黄牌警告——

换个说法，把道理讲出来。

🎯
对比一下两种写法

差的："NEVER 用紫色背景。"
好的："避免紫色背景——因为它和我们的品牌色冲突，会让用户混淆两家公司。" 讲清为什么，AI 遇到没见过的情况也能举一反三；只下命令，换个场景它就抓瞎。

怎么测？关键招式：对照实验

评估一个技能好不好，光看它"能不能用"是不够的。要回答一个更狠的问题："比我直接让 AI 干，强在哪？" 仓库的做法是跑对照实验（同时起两个 子代理，一个带技能一个不带）：

skill-creator/SKILL.md 

For each test case, spawn two
subagents in the same turn -- one
with the skill, one without.

**With-skill run:**
- Skill path: <path-to-skill>
- Task: <eval prompt>

**Baseline run** (same prompt):
- no skill at all
- save to without_skill/outputs/
逐行翻译

每个测试问题，同时起两个子代理……

一个带着技能，一个不带。

带技能的那组：

给它技能路径 + 同一个任务。

基线组（同样的问题）：

完全不给技能。

两份结果存到不同文件夹，拿来对比。

💡
这是科学实验的思维

只有一个变量（有没有技能），其他全相同（同一个问题、同一时间跑）。如果带技能的明显更好，才能证明"这技能真有用"。否则可能只是这个问题恰好简单、谁都能答好——你误以为是技能的功劳。这种"对照"思想，是你日后评估任何 AI 工具的通用武器。

迭代中藏着一个金矿：发现"重复劳动"

这是仓库里最实用的洞察之一。当你跑测试、读子代理的对话记录时，要留意一种信号：

skill-creator/SKILL.md 

Look for repeated work across
test cases. Read the transcripts
from the test runs and notice if
the subagents all independently
wrote similar helper scripts... If
all 3 test cases resulted in the
subagent writing a create_docx.py,
that is a strong signal the skill
should bundle that script.
逐行翻译

留意跨测试用例的重复劳动。

去读测试运行的完整对话记录……

看子代理们是不是各自独立地写了相似的辅助脚本。

举个例子：如果 3 个测试里……

子代理都各自写了一个 create_docx.py……

这就是个强信号——

说明这个脚本应该直接打包进技能的 scripts 文件夹，让以后每次调用都现成的。

💡
这条原则的威力在于"举一反三"

它的本质是：如果 AI 每次都要现造同一个轮子，那就把这个轮子预先造好。这个思想不只适用于技能——你日常用 AI 时，如果发现它反复写同一段代码、同一个函数，就该把那段沉淀成可复用的片段。识别"重复"是工程效率的核心直觉。

打磨好了，怎么交付？打包成 .skill

迭代满意后，最后一步是打包。package_skill.py 把整个文件夹压成一个 .skill 文件（本质是个 zip），方便分发安装。看它的核心逻辑：

skill-creator/scripts/package_skill.py 

# Patterns to exclude
EXCLUDE_DIRS = {"__pycache__",
  "node_modules"}
EXCLUDE_GLOBS = {"*.pyc"}
# Excluded only at skill root
ROOT_EXCLUDE_DIRS = {"evals"}

# Run validation first
valid, msg = validate_skill(skill_path)
if not valid:
  return None  # 拒绝打包
逐行翻译

打包时会排除一堆不该带走的东西。

__pycache__、node_modules——这些是运行时的缓存垃圾。

*.pyc——编译过的临时文件。

还有根目录下的 evals——测试用例不打包进去（体积大，且用户不需要）。

打包前先跑一遍校验。

校验不过（字段名错、超长等）……

直接拒绝打包——把次品拦在出厂前。
